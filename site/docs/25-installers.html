One command

aletheia install claude-code --write
aletheia install command-code --write

Without --write the command is a dry run: it prints every step and changes nothing. aletheia uninstall <tool> --write removes only the entries the install manifest lists. Every changed file gets a copy named <file>.aletheia-bak-<timestamp>.

The manifest is <data dir>/install-manifest.json. The default data dir is ~/.aletheia.

What Command Code gets

StepFileWhat is written
MCP~/.commandcode/mcp.jsonmcpServers.aletheia = {transport: "stdio", command: <bun>, args: [<mcp.mjs>]}
Hooks~/.commandcode/settings.jsonOne entry per event under hooks.<Event>; permissions and other settings are kept

Hooks: SessionStart (injects context on startup and clear, silent on resume), PostToolUse (stores tool events), Stop (queues compression).

What Command Code cannot capture. It has no UserPromptSubmit hook, no SessionEnd hook, and its SessionStart source is startup | resume | clear with no compact. Prompts and session-end summaries are therefore not captured there. The installer prints this, and the install manifest records it. Do not claim otherwise in the README.

The hook command

Each entry runs:

<bun> <data dir>/aletheia.bundle.mjs hook <tool> <event> # aletheia-managed

The absolute Bun path avoids a PATH lookup. The trailing comment is the marker used by uninstall and doctor. apply builds the bundle with Bun's built-in bundler; if that fails it points the hooks at bin/aletheia.mjs instead. The bundle exists because a hook has a ~100 ms budget: loading a dozen modules costs more than the work.

Hook runtime guarantees

  • Exit code is always 0. Broken JSON, an unknown event, a missing store or an internal error never blocks the host.
  • No network call and no model call. Compression is queued, not run in the hook.
  • Text is redacted before it is stored (src/hub/redact.mjs). <private> blocks are dropped.
  • If the database cannot be opened, the already-redacted item is appended to <data dir>/spool/hook-spool.jsonl. The next successful hook flushes the spool.
  • Recalled context is wrapped in <aletheia-memory> with a line saying it is data, not instructions.
  • The entry point has a 150 ms watchdog and always returns.

Rule hygiene

aletheia rules lint [--dir path] [--tools a,b] [--json] checks the store and the managed blocks before a sync. It reports duplicate rules once per group, direct always/never contradictions with the same scope and condition, a rule over 300 characters, an enabled set over 4,000 characters, instructions that ignore safety (ignore previous instructions, bypass security, rm -rf /, ...), and text that matches the redaction patterns (a secret). For every managed block that exists under the project directory or the user home it compares the parsed bullets with the enabled store rules: a rule only in the file and a rule only in the store are both drift, each with the file and line or the rule id. Each finding has a fix hint.

The check is a warning, not a gate: rules sync still runs. --json returns {findings, checked}. A file without the managed-block markers is skipped, so a user's own CLAUDE.md/AGENTS.md text is never compared.

Stale rules are reported too: stale_rule is a warning with the fix hint "confirm or retire", raised when a rule's evidence went stale or nobody confirmed it within the review window (rules.reviewDays, default 90). It is a flag: the rule stays enabled and rules sync still writes it. See docs/03 for the reasons.

aletheia rules confirm <id> records that a rule is still right (its last-confirmed date becomes now) and writes an audit row. aletheia rules retire <id> turns a rule off without deleting it. aletheia rules list [--stale] [--older-than N] prints each rule with its date, source and a [re-check: ...] marker.

Where the tools disagree

aletheia rules diff [--dir path] [--tools a,b] [--json] (and GET /api/hub/rules/diff) compares each tool's managed block with the store. Per file it lists rules only in the store (with the rule id), rules only in the file (with the line), and rules whose wording differs (store text, file text and line), then a count of tools out of sync. It never writes. A file without the managed-block markers is reported as not compared. The Rules page shows the same count.

Transcript watcher

Tools without hooks can still be imported from their session files. aletheia watch polls the three verified layouts, keeps a byte offset and turn counter per file in ~/.aletheia/watcher.db, and imports only new lines:

aletheia watch --once
aletheia watch --interval 1000 --batch 50 --tool claude-code,command-code,codex
ToolFolderVerified from
Claude Code~/.claude/projects/<slug>/<session>.jsonl2026-10-26
Command Code~/.commandcode/projects/<slug>/<session>.jsonl2026-10-26
Codex CLI~/.codex/sessions/<year>/<month>/<day>/rollout-*.jsonltwo real rollouts on this machine, 2026-10-26

The source files are opened read-only. A file that shrinks is re-read from zero. A line without a newline is left for the next pass. A JSON line the parser does not recognise, and a line that is not JSON, are stored as a kind = "raw" episode instead of being dropped. The polling loop is clamped to at least 1000 ms, takes a batch size per file, and the CLI sets nice 10. Restarting resumes at the stored offset; a re-read is deduped by source_ref and content hash.

End-to-end test

test/e2e-more-hosts.test.mjs installs all six full-capability hosts into a temp HOME, reads the command back from each config, pipes a recorded payload set through it, and checks rows, redaction and p95. On 2026-10-26: 2 tests pass, p95 1.24 to 2.48 ms per host (hook work only). This is the real installed command, not a call to the adapter; it is still not the host application.

Check hooks in a real session

The fixtures prove the installed hook command, not the host. To check a real session, use a throwaway HOME, a throwaway project and a throwaway data directory so nothing touches the real ~/.aletheia, ~/.claude or ~/.commandcode:

root=$(mktemp -d /tmp/aletheia-hook-check.XXXXXX)
mkdir -p "$root/home" "$root/project"
cd "$root/project"
export HOME="$root/home"
export ALETHEIA_DATA_DIR="$root/data"
export ALETHEIA_PORT=37890
aletheia install command-code --write
aletheia install claude-code --write
aletheia install codex --write

Start one short session in Command Code, Claude Code or Codex CLI in this project with the same HOME, send one prompt and one file-reading tool call, then end the session. Codex requires the non-managed hooks to be reviewed once with /hooks before they run. Run the checker on the data directory it wrote:

bun scripts/hook-check.mjs "$ALETHEIA_DATA_DIR" --tool command-code
bun scripts/hook-check.mjs "$ALETHEIA_DATA_DIR" --tool claude-code
bun scripts/hook-check.mjs "$ALETHEIA_DATA_DIR" --tool codex

scripts/hook-check.mjs opens hub.db read-only and prints the sessions seen, events per hook type, the first and last timestamp, whether any stored text still matches a redaction pattern (reported as a row and column, never the secret), whether the spool is empty, and a PASS/FAIL per expected event. It exits 1 on any FAIL.

What a real session captures per tool:

ToolCapturedNot captured
claude-codeSessionStart context (injected, no stored row), UserPromptSubmit (prompt), PostToolUse (tool event), Stop and SessionEnd (summary)nothing in its five-event set
command-codeSessionStart context (injected, no stored row), PostToolUse (tool event), Stop (session end)UserPromptSubmit and SessionEnd: Command Code has no such hooks, so prompts and session-end summaries are not captured
codexSessionStart context (injected, no stored row), UserPromptSubmit (prompt), PostToolUse (tool event), Stop and SessionEnd (summary)nothing in its five-event set

Command Code has no UserPromptSubmit or SessionEnd hook, so the checker marks those two events "not installed" instead of FAIL. SessionStart injects context but stores no row, so it is reported as context-only and cannot be confirmed from the database. For Claude Code and Codex, the checker counts the summary memory as the Stop/SessionEnd signal and falls back to the session-end table when that has rows and there is no summary.
